# 歌声音域推定ツール 設計案

MV等の音源から、楽曲ごとの **地声最高音 / 裏声最高音** を自動推定するツールの設計。

---

## 0. 前提と注意

- YouTube からの音声ダウンロードは YouTube 利用規約に抵触する可能性がある。開発・評価は手持ち音源／購入音源／CC ライセンス音源を主軸にし、URL 入力は「ローカルファイル入力の一形態」として実装しておくのが安全（`ingest` を差し替え可能にする）。
- 音域まとめサイトのラベル収集も、robots.txt・利用規約の確認とレート制限（1req/2s 程度、User-Agent 明示、ローカルキャッシュ）が前提。取得したラベルは**手元の学習用途に限定**し再配布しない。

---

## 1. いちばん重要な発想の転換

### 1-1. 「全フレームのレジスター分類」は要らない

素直に考えると「歌声の全区間を地声/裏声に分類する器」を作りたくなるが、**欲しい出力は曲ごとに 2 つの数字だけ**。

つまり実際に判定が必要なのは、**その曲で検出された音のうち上位 10〜20 個**だけ。
これが効いてくる：

- 人手ラベリング量が 1/100 以下になる（1 曲 20 ノート × 100 曲 = 2000 サンプルで十分な規模になる）
- 能動学習（判定が曖昧な上位ノートだけ人に聞かせる）が自然に成立する
- 推論も軽い（分離と F0 抽出が支配的で、分類器は誤差レベル）

### 1-2. サイトのラベルは「曲単位の弱ラベル」

`地声最高音 = hiA` は「この曲の地声ノート集合の max が A4」という**集合レベルの制約**であって、
どのノートが地声かは教えてくれない。これは **Multiple Instance Learning (MIL)** そのもの。

ただし制約から**タダで擬似ラベルが取れる**のが美味しい：

| 条件 | 導かれること | 確度 |
|---|---|---|
| ノートのピッチ > 地声最高音 + 1半音 | そのノートは地声ではない（＝裏声 or 検出ミス） | **高** |
| ノートのピッチ > 裏声最高音 + 1半音 | 検出ミス／ハモリ／ノイズ | **高**（クリーニングに使える） |
| ピッチ == 地声最高音 付近で最頻・最長 | 地声の陽性例 | 中 |
| ピッチ < パッサージョ - 3半音 | ほぼ地声 | 中（裏声で低音も出せるので弱い） |

→ **上限制約が「負例の自動生成器」として働く**。ここが弱教師で回せる根拠。

### 1-3. `max` は壊れやすい統計量

1 フレームの誤検出で答えが変わる。ハモリ・コーラス・シャウト・ノイズが全部効く。
対策として **最初から `max` を使わない**：

> 「持続 ≥150ms、ピッチ安定（cents 標準偏差 < 50）、有声確信度 ≥ 閾値、かつ曲中 2 回以上出現」
> を満たすノートの最高値

さらに保険で 99.5 パーセンタイルも併記して乖離を監視する。これだけでサイトラベルとの一致率がかなり上がるはず。

## 2. パイプライン

```
[入力] mp3/wav (or URL)
   │
   ├─ 1. 音源分離           Demucs (htdemucs) or BS-Roformer → vocals stem
   │      └─ リード抽出     Mid/Side 処理でセンター成分強調（ハモリはサイドに広い）
   │
   ├─ 2. F0 推定            RMVPE（歌声に強い）/ torchcrepe / pyin
   │      └─ 後処理         Viterbi 平滑化 + オクターブ誤り検出
   │
   ├─ 3. ノート化           半音量子化 → 安定区間セグメント化 → 各ノートの中央値 cents
   │      └─ フィルタ       最短長・安定度・有声確信度・エネルギー
   │
   ├─ 4. 候補選抜           ピッチ上位 N=20 ノートのみ次段へ
   │
   ├─ 5. レジスター分類     地声 / 裏声 (/ ノイズ) を各候補に付与  ★ここが本体
   │
   └─ 6. 集約               ロバスト統計で 地声最高音 / 裏声最高音 を確定
          [出力] JSON + 根拠（該当ノートの時刻・波形切り出し）
```

### オクターブ誤りの検出（地味だが致命的）

裏声の高音では F0 推定器が 1 オクターブ下に落ちることがあり、逆に倍音を掴んで 1 オクターブ上に飛ぶこともある。
推定 F0 に対して以下をチェック：

- 推定 F0 の位置にスペクトルピークが実在するか
- F0/2 の位置にピークが**無い**か（あれば実際はそちらが基本波）
- ノート内でのオクターブジャンプは平滑化で潰す

## 3. 地声 / 裏声の判別（本丸）

### 3-1. 音響的な手がかり

音声科学的には modal（地声）と falsetto（裏声）は声帯の振動様式が違い、以下に現れる：

| 特徴量 | 裏声での傾向 | 実装 |
|---|---|---|
| **H1-H2**（第1・第2倍音の振幅差） | 大きい（開放商が高い） | 自前 or opensauce |
| **H1-A1 / H1-A3** | 大きい | 声道フィルタ補正付き |
| **スペクトル傾斜 / 高域エネルギー比** | 急峻（高域が薄い） | librosa |
| **シンガーズフォルマント帯 (2.5–3.5kHz)** | 弱い（ベルト声で強い） | 帯域エネルギー比 |
| **CPP（ケプストラルピーク顕著性）** | 低い（息成分が多い） | parselmouth |
| **HNR** | 低い | parselmouth |
| **ビブラート深さ・レート** | 浅くなりがち（個人差大） | F0 軌跡の FFT |
| **直前ノートからの跳躍幅・時間ギャップ** | 大きい（レジスターブレイク） | 文脈特徴 |
| **F0 の歌手内相対位置** | 高い | ★下記 |

### 3-2. 歌手内正規化がほぼ必須

男女・声種で絶対音高の意味が全く違う。A4 は男性なら裏声寄り、女性なら地声の常用域。
そこで **曲（＝歌手）ごとの F0 分布統計**（中央値、10/90 パーセンタイル）で正規化した相対ピッチを特徴に入れる。
これを入れるかどうかで精度がかなり変わるはず。

### 3-3. モデルの段階

| 版 | 手法 | 必要データ | 学習コスト |
|---|---|---|---|
| **v0** | ヒューリスティック（推定パッサージョ + スペクトル傾斜の閾値） | 0 | 0 |
| **v1** | 手設計特徴 + LightGBM | 数百ノート | 数秒 |
| **v2** | **凍結 SSL エンコーダ + 線形プローブ**（WavLM / HuBERT / MERT の中間層） | 数百ノート | 数分（GPU） |
| **v3** | log-mel パッチ CNN + 手設計特徴 concat、弱教師で全曲学習 | 数千曲 | 数十分〜 |

**個人 PC 前提なら v2 が最もコスパが良い。** 事前学習済みモデルは凍結して特徴抽出器として使うだけなので、
実際に学習するのは線形層 or 小さな MLP のみ。数百サンプルでも十分に立ち上がる。
v1 は解釈性が高く「何が効いているか」を見るのに有用なので、v1 と v2 は並走させて比較するのが良い。

### 3-4. 弱教師（MIL）の定式化 — v3 向け

曲 `s` のラベルを `c_s`（地声最高音）, `f_s`（裏声最高音）、ノート `i` のピッチ `p_i`、裏声確率 `q_i` とする。
微分可能な soft-max（log-sum-exp, 温度 τ）で推定値を作る：

```
ĉ_s = LSE_τ( p_i + λ·log(1 - q_i) )     # 地声側の soft-max
f̂_s = LSE_τ( p_i + λ·log(q_i)     )     # 裏声側の soft-max
L   = Huber(ĉ_s - c_s) + Huber(f̂_s - f_s) + α·Σ ReLU(p_i - f_s - 1)
```

第 3 項は「ラベルの裏声最高音を超えるノートは検出ミス」というクリーニング項。
これでノートレベルのラベルなしに、曲レベルのラベルだけで `q_i` を学習できる。

## 4. 教師データ戦略

推奨は **シード → 能動学習 → 弱教師スケール** の 3 段。

1. **シード（最重要・最初にやる）**
   自分で 30〜60 分ぶん、地声と裏声を音階で録音する。ラベルが完全に正しい唯一のデータで、
   特徴量が本当に効くかの検証に使える。ここで H1-H2 等が分離しないなら設計を疑うべき。
2. **能動学習ラベリング**
   §1-1 の通り、1 曲あたり上位 20 ノートだけを人が聞いて `1=地声 / 2=裏声 / 3=ノイズ` を押す UI を作る。
   1 曲 1〜2 分。50 曲で 1000 ノート。**ここが一番の投資対効果**。
   分類器の確信度が低いノートを優先提示すれば効率がさらに上がる。
3. **弱教師スケール**
   サイトのラベル（曲単位）で §3-4 の MIL 損失を回し、数千曲規模へ。

**公開データセット候補**（要現物確認、ライセンスも要確認）：
VocalSet（歌唱技法ラベル付き。belt / breathy 等がレジスター判別の代理になり得る）、
NUS-48E、OpenSinger、M4Singer、Opencpop。
ただしレジスターを直接ラベルしたデータセットは乏しいので、過度に期待しない方がよい。

## 5. ラベルの品質問題（無視すると評価が壊れる）

- **ミックスボイスの扱いがサイトごとに違う。** 地声に含めるサイト/含めないサイトがある。同一サイトでも記事によってブレる。
- **アドリブ・フェイク・シャウトの扱いが違う。** 「最高音」がサビの決め音を指すか一瞬の叫びを指すかが不定。
- **ハモリ・コーラスが混入した記載**がある。
- 対策：
  - ソースを 1 サイトに固定して**規約を揃える**（複数サイト混在は最後にやる）
  - ±1 半音の許容で評価する
  - ノイズ耐性のある損失（Huber, ラベルスムージング）を使う
  - 学習前に「明らかに矛盾する曲」（地声最高音 > 裏声最高音 など）を弾く

---

## 6. 評価

- 主指標：半音単位の絶対誤差 MAE、および **±0 / ±1 / ±2 半音以内の一致率**（地声・裏声を分けて）
- 必ずベースラインと比較する：
  - B0: 「全ノートの max = 裏声最高音、パッサージョ推定値以下の max = 地声最高音」
  - B1: v0 ヒューリスティック
- 曲は **アーティスト単位で** train/valid/test 分割する（同一歌手のリークを防ぐ）
- エラー分析用に、外した曲の該当ノートの音声を切り出して保存する仕組みを最初から入れる

## 7. 日本語音名表記の変換

音域サイトは `mid2G#` / `hiA` / `hihiC` といったカラオケ表記を使う。**オクターブの境界が A** である点に注意
（C ではない）。対応表：

| 表記帯 | 範囲 | 例 |
|---|---|---|
| `lowlow` | A0 – G#1 | |
| `low`    | A1 – G#2 | `lowF` = F2 |
| `mid1`   | A2 – G#3 | `mid1C` = C3 |
| `mid2`   | A3 – G#4 | `mid2C` = C4, `mid2G#` = G#4 |
| `hi`     | A4 – G#5 | `hiA` = A4, `hiC` = C5 |
| `hihi`   | A5 – G#6 | `hihiA` = A5 |

（採用するサイトの表記が本当にこの規約かは、既知の曲でスポットチェックして確認すること。）
内部表現は **MIDI ノート番号（float, cents 保持）** に統一し、入出力でだけ変換する。

## 8. リポジトリ構成案

```
pitch/
├── pyproject.toml
├── src/vocalrange/
│   ├── ingest/        # ファイル読み込み・URL 取得・キャッシュ
│   ├── separate/      # Demucs / BS-Roformer ラッパ、Mid/Side リード強調
│   ├── f0/            # RMVPE / CREPE ラッパ、Viterbi 平滑化、オクターブ補正
│   ├── notes/         # セグメント化・フィルタ・候補選抜
│   ├── features/      # H1-H2, CPP, HNR, spectral tilt, mel patch, SSL 埋め込み
│   ├── register/      # 地声/裏声分類器（v0 heuristic / v1 gbdt / v2 probe / v3 mil）
│   ├── aggregate/     # ロバスト集約 → 地声最高音・裏声最高音
│   ├── labels/        # 音名表記パーサ、参照ラベルの正規化・検証
│   ├── eval/          # 指標・エラー分析・音声切り出し
│   └── cli.py
├── tools/label_ui/    # 能動学習ラベリング UI (Streamlit)
├── data/              # gitignore（キャッシュ・音源・ラベル DB(SQLite)）
└── tests/
```

CLI イメージ：

```bash
vocalrange analyze song.mp3 --json
vocalrange batch  data/songs/ --db data/notes.db
vocalrange label  --db data/notes.db          # ラベリング UI 起動
vocalrange train  --model probe --db data/notes.db
vocalrange eval   --db data/notes.db --refs data/refs.csv
```

出力 JSON イメージ：

```json
{
  "chest_max":     {"midi": 69, "name": "A4",  "jp": "hiA",  "time": 142.3, "confidence": 0.87},
  "falsetto_max":  {"midi": 74, "name": "D5",  "jp": "hiD",  "time": 168.9, "confidence": 0.71},
  "notes_analyzed": 412,
  "candidates": [ ... ]
}
```

**中間成果物を必ず DB に永続化**すること。分離と F0 抽出が全処理時間の大半なので、
分類器を作り直すたびに再計算するのは無駄。ノート単位の特徴量まで保存しておけば学習ループが秒で回る。

## 9. 進め方（推奨順）

| Phase | 内容 | 得られるもの |
|---|---|---|
| **0** | 分離 → F0 → ノート化 → v0 ヒューリスティックまで一気通貫。参照ラベル 50 曲で評価 | ベースライン数値。**ここで初めて問題の難しさが分かる** |
| **1** | 自己録音でシードデータ作成、特徴量の分離性を検証 | 特徴設計の妥当性 |
| **2** | ラベリング UI + 能動学習で 50〜100 曲ラベル、v1/v2 学習 | 実用精度の本命 |
| **3** | ラベル収集を数千曲に拡大、MIL で v3 学習 | スケール |

**Phase 0 を飛ばさないこと。** 分離と F0 とノート化の品質が悪ければ、どんな分類器を載せても意味がない。
逆に Phase 0 の時点でベースラインが ±2 半音に収まるなら、残りは分類器の勝負に絞れる。

## 10. 主要ライブラリ

| 用途 | 候補 |
|---|---|
| 音源分離 | `demucs` (htdemucs) / `audio-separator` (BS-Roformer, MDX-Net) |
| F0 推定 | RMVPE（歌声に最も強い）/ `torchcrepe` / `librosa.pyin` |
| 音響特徴 | `librosa`, `praat-parselmouth`(CPP/HNR/harmonics), `opensauce-python` |
| SSL 埋め込み | `transformers` の WavLM / HuBERT、音楽なら MERT |
| 分類器 | `lightgbm`, `torch` |
| 保存 | SQLite / DuckDB + Parquet |
| UI | `streamlit` |
| 前処理 | `ffmpeg`, `yt-dlp`（入力経路の一つとして） |

処理時間の目安（GPU あり、1 曲 4 分）：分離 10–30s、F0 5s、特徴量 5s。
100 曲で 1 時間弱。**学習より前処理が支配的**なので、キャッシュ設計が事実上の性能設計になる。
